Phase 1 · Research

Map the thing before you touch it

Brief the agent for one job: just the map of X, where X is the thing being changed (e.g. "who calls the auth module?").

The brief

  • Don't ask for solutions — only the map
  • If the docs suck, don't read them — read the code
  • Output is a research artifact, not a fix

What the artifact must contain

  • Subject of the map (e.g. the auth module)
  • Callers — who actually calls the functions / classes / APIs
  • Docs — do they exist, are they accurate, when last updated
  • Relationships between the pieces
  • Notes — anything interesting or off
  • Static analysis to back it up

Goal of this phase: an accurate picture. No changes proposed yet.

Phase 2 · Grill & Align

Agree on the goal, and how hard it is

You must be able to state the goal in one sentence. Then size the task before planning it.

Nomenclature

Everyone agrees on the name of stuff. Shared vocabulary first.

How hard is it?

Simple (e.g. changing a button colour) → no need to grill, unless you want to.

Hard → grill me first.

Alignment

You and the agent both agree on direction before any work starts.

Grill me→ Define goal in one sentence→ Aligned
Phase 3 · Plan

Turn the map into a safe plan

Four things get decided before the agent writes code. The next slides cover each.

① Risk / Blast radius

How much can this break? More touches = more risk.

② Guardrails — hard rules of what NOT to do

Vibes, common sense, taste. Do-not list.

③ Deterministic hard checks

Tests, linters, AST/grep — pass or fail.

④ Tickets

Small, junior-executable units of work.
Phase 3 · Plan — Risk

Complexity is the blast radius

Difficulty isn't about the code you write — it's about how far a change reaches. More touches, more risk.

Blast radius

How many places feel this change?

Failure radius

If it breaks, how far does the damage spread?

Untested code

No tests = you can't see the blast. Higher risk.

Conflicting SSOTs

Two "sources of truth" that disagree — a trap.

Static analysis

Run it across all the callers / APIs to find the real reach.

Limit the damage

Scope the change so failure stays contained.

Phase 3 · Plan — Guardrails

Hard rules of what NOT to do

The "vibes / common sense / taste" layer, written down so the agent can't wander.

Do not change downstream callers

Stay inside the scope you mapped.

Do not introduce new APIs / classes

Work with what exists.

Do not make new files

No sprawl.

Do not keep growing the single god file

Don't pile onto the thing that's already too big.

If a check fails — stop. A broken guardrail ends the attempt.

Phase 3 · Plan — Checks & Tickets

Make "done" mechanical

Deterministic hard checks / gates

  • Tests
  • Linters
  • AST / grep
  • Static analysis

Pass or fail — no opinion needed.

Tickets

The test of a good ticket:

"If I hand this to a junior, can they execute from only this document?"

Ticket 1→ Ticket 2→ Ticket 3

Tickets v2 = tickets + journal (Phase 5 feeds back here).

Phase 4 · Execute

One ticket at a time, gated

Take a ticket, let the agent try, run the checks. The gate decides what happens next.

Take ticket 1→ Let the agent try→ Run checks→ Failed?

Pass

Move to the next ticket.

Fail

Let the agent try again — but stop if it breaks repeatedly, multiple times, or hits a complete non-negotiable.

Repeated failure usually means you didn't define or prepare the agent for success — back to Plan.

Phase 5 · Journal / Ledger of work

The flywheel

Every attempt — win or fail — is recorded and feeds the next one.

Failure

Logged, not hidden. It's data.

Multiple attempts

The ledger holds what was tried and why it broke.

Flywheel

Each pass makes the next attempt sharper.

Attempt→ Journal it→ Better tickets (v2)↻ Next attempt

The loop closes back into Phase 3: tickets v2 = tickets + journal.
