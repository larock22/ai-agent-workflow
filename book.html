Book One

The Foundation

The Six Pillars

The new foundation — locked

Pillars 1–3

Structure, Feedback, Quality

PILLAR 1
The codebase is the interface
Mapped modules, ownership, allowed dependencies, progressive disclosure of agent instructions — all enforced in CI, not left to convention. The repository continuously proves an agent can navigate it safely.
enforced in CI
PILLAR 2
Sensors and guides create continuous feedback
Sensors observe; guides encode what the organization has learned. Recurrence is the signal: one occurrence is noise, repetition is a missing rule. The promotion loop turns mistakes into permanent organizational knowledge.
finding → guide → enforcement
PILLAR 3
Traditional quality still matters — more
Hammer the types: invalid states unrepresentable. Hammer the interfaces: control surfaces an agent can't exploit. Data-flow maps are now cheap — generate them and check them against the real code.
verified map > fictional diagram

Pillars 4–6

Infrastructure, Fault, Workflow

PILLAR 4
Infrastructure matters more than ever
Controlled runners, sandboxes, worktrees, tested backups, supply-chain rules. Design the environment as though the agent will eventually destroy something — because it will.
assume destruction
PILLAR 5
Every agent mistake is your fault
A repeated agent failure is evidence of a missing engineering control. Every incident feeds the flywheel: mistake → analysis → missing control → improvement. Never use future capability as an excuse for weak systems today.
make the lint stricter
PILLAR 6
Agentic development requires an explicit workflow
Research, align, plan, execute, journal — one ticket at a time. The work is not complete when the patch lands; it is complete when the system has learned from it.
complete = learned

Voice & Rules

How the book sounds — and what is never violated

Locked

The Voice

  • Terse, imperative, law-like. Titles read like laws: “Primitives Before Prompts,” “Fail with Instructions,” “Hammer Your Types.”
  • One hand wrote this book. Clipped, rule-stating cadence throughout.
  • No history. No model-release timelines. Chapter 1 states the premise and moves.
  • Honest about open problems. The skeptical reader smells overclaiming instantly.
  • Prose-first. Code blocks now permitted — but only when one block does the work of a page. ASCII diagrams become designed figures.
“
A backup that has never been restored is only a theory.
Aphorisms are load-bearing · coin them deliberately, don’t dilute them

Never violate

The Four Hard Rules

RULE 1
No internal names in manuscript
Never mention the internal project name, the Roman candidate names (Lex Imperium, Custos, Praetor, Vinculum, Ordo, …), or the author’s internal interface specifics.
RULE 2
Attribute borrowed frameworks
Name the source — OpenAI, Stripe, Anthropic, LangChain — and clearly mark the book’s own extensions.
RULE 3
Paraphrase, don’t quote
Never quote sources at length. Quotes stay under 15 words and are rare.
RULE 4
No single-vendor theses
Never rest a claim on a vendor’s post about its own product; always pair with independent corroboration. Applies to Droid CLI agent-readiness and Shai-Hulud before they carry weight.

Rule 1 · default ruling, flip if wrong

The Sentinel Ruling

  • Sentinel is the public companion project — it may be named in manuscript.
  • Its concepts are book vocabulary: observe/evaluate/render, typed findings, recurrence thresholds, guide candidates, code-first configuration.
  • Never conflate: a completed run with a failing verdict vs. a faulted run.
  • Implementation internals stay out — package layout, CLI invocations, state-file paths.
  • At most one illustrative config block per chapter.
